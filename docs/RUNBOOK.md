# Эксплуатационный runbook

Документ описывает безопасные действия при деплое и инцидентах. Он не разрешает
удалять production-данные, сбрасывать БД или обходить проверки доступа.

## Проверка после деплоя

1. Railway deployment имеет статус `Success`.
2. `GET /api/health` отвечает `200`, `ok: true`, `storage: "postgres"`.
3. Открывается форма входа без ошибок CSP в консоли.
4. Основатель входит с актуальным `AUTH_*_PASSWORD`.
5. Открываются Главная, Заявки, Проекты, Деньги и Себестоимость.
6. На мобильном viewport открываются drawer и bottom-sheet.
7. Выполняются `npm test` и QA против отдельного тестового окружения.

Production QA нельзя запускать, если сценарий создаёт или меняет реальные
сущности. Стресс-скрипты предназначены для локального/тестового окружения.

## Обязательные Railway Variables

- `NODE_ENV=production`
- `SESSION_SECRET` — длинный случайный секрет
- `DATABASE_URL=${{Postgres.DATABASE_PRIVATE_URL}}`

Bootstrap-аккаунт создаётся или синхронизируется только если задан его
`AUTH_<KEY>_PASSWORD`. Пароль — не менее 12 символов. Email можно переопределить
через `AUTH_<KEY>_EMAIL`; иначе используется адрес аккаунта из `lib/auth.js`.
`__SET_ME__` считается отсутствующим значением.

Нельзя задавать `ALLOW_DEV_BOOTSTRAP=1` в production.

## Ротация пароля пользователя

1. Основатель открывает «Команда» в нижней части навигации.
2. Сбрасывает пароль нужного пользователя.
3. Передаёт новый пароль через согласованный защищённый канал.
4. Старые сессии пользователя становятся недействительны автоматически.

Если пароль задаётся через `AUTH_*_PASSWORD`, после изменения Railway
перезапускает сервис. На старте хеш обновляется только когда секрет реально
изменился; активные старые сессии отзываются.

## Ротация `SESSION_SECRET`

Ротация немедленно завершает все активные сессии.

1. Убедиться, что у основателя есть актуальный входной пароль.
2. Заменить `SESSION_SECRET` в Railway Variables.
3. Дождаться успешного redeploy.
4. Проверить health и повторный вход.

Не хранить старый или новый секрет в тикетах, git и логах.

## Пользователь не может войти

Проверять по порядку:

1. Health endpoint доступен и PostgreSQL отвечает.
2. Email совпадает с `AUTH_*_EMAIL`, если переменная задана; иначе — с
   `defaultEmail` аккаунта из `lib/auth.js`.
3. `AUTH_*_PASSWORD` не пустой, не `__SET_ME__` и содержит 12+ символов.
4. После изменения Variable завершился новый deployment.
5. Пользователь не отключён.
6. Нет ответа `429`; при нём соблюдать `Retry-After`, не продолжать перебор.
7. Очистить только cookies сайта и выполнить новый вход.

Не ослаблять rate-limit и не возвращать известные fallback-пароли.

## Ошибка запуска

`SESSION_SECRET` / `DATABASE_URL` отсутствует:

- добавить переменную в Railway;
- не заменять PostgreSQL файловым хранилищем в production.

`Нет пользователей`:

- задать хотя бы один валидный `AUTH_*_PASSWORD`;
- не возвращать пользователей с паролями в `data/seed.json`.

Ошибка TLS PostgreSQL:

- для Railway использовать private URL;
- для публичного PostgreSQL задать проверяемый `DATABASE_CA`;
- не включать `rejectUnauthorized: false`.

Ошибка миграции:

- остановить rollout;
- сохранить текущий deployment и логи;
- проверить совместимость схемы;
- исправить миграцию вперёд, не удаляя таблицы и данные.

## Инцидент: рост неудачных входов

1. Проверить логи `401`/`429` и временной диапазон.
2. Не публиковать email и IP из логов.
3. При подозрении на компрометацию сменить пароль пользователя.
4. При компрометации общего секрета ротировать `SESSION_SECRET`.
5. Сохранить техническую хронологию без секретов.

Лимиты хранятся в `login_rate_limits`; ключи IP/email записаны как SHA-256.
Ручная очистка таблицы в production не является штатным способом разблокировки.

## Инцидент: белый экран / сломанная навигация

1. Зафиксировать URL, роль, viewport и сообщение консоли.
2. Проверить, что загружены cache versions из `public/index.html`.
3. Запустить `npm run qa:ui` локально на том же commit.
4. Проверить `window.__gsNavigate`, отсутствие `.sidebar` и наличие `#gs-nav`.
5. Исправить первопричину и поднять cache version.

Нельзя добавлять DOM-click fallback к скрытой навигации.

## Откат

Откатывается код/deployment, но не база данных.

1. Выбрать последний проверенный commit/deployment.
2. Убедиться, что старая версия совместима с текущей схемой и payload.
3. Выполнить Railway redeploy проверенной версии.
4. Проверить health, вход и критические разделы.
5. Исправить проблему отдельным forward-fix.

`git reset --hard`, удаление `os_state`, восстановление seed поверх production и
ручное удаление сущностей не входят в процедуру.

## Резервное копирование

- Использовать snapshots/backups PostgreSQL, предоставляемые инфраструктурой.
- Перед изменением структуры данных убедиться в наличии актуального backup.
- Проверять восстановление на отдельной БД/окружении.
- Никогда не тестировать restore поверх рабочей production-БД.
